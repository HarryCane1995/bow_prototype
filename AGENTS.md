# BowPrototype agent instructions

Read `Docs/CODEX_RULES.md` before broad code or scene changes. Preserve unrelated working-tree changes and keep imported level wrappers lightweight.

## Blender and Godot asset workflow

- Blender MCP is available for this project. For map geometry, models, UVs, textures, or Blender materials, inspect the corresponding `.blend` source first and prefer Blender MCP / Blender Python API over UI-coordinate clicks.
- The canonical Level_01 map source is `res://Level_01_Blockout.blend`. Godot imports it directly as a `PackedScene`, and `res://Scenes/Levels/Level_01/Level_01.tscn` instances it as `ImportedLevel`.
- Editable sources are `.blend` files and repository textures. `.godot/imported/*` and Godot's imported scene are generated; never edit them. There is no production Level_01 `.glb` in the selected pipeline. If a generated `.glb/.gltf` fallback is introduced later, never edit it instead of its `.blend` source.
- Keep Level_01 textures under `res://Assets/Textures/Levels/Level_01/` and store Blender paths as `//Assets/Textures/Levels/Level_01/...`; do not add user-specific absolute paths or pack large images without a documented reason.
- After a Blender change: save `Level_01_Blockout.blend`, run/retrigger Godot import, load the imported scene, and run the map. A 3D asset task is not complete until the result is verified in Godot.
- Do not destructively rebuild the root map, mass-apply transforms, or overwrite the Godot wrapper without an explicit request. Geometry/UV/base materials belong in Blender; C# logic, runtime triggers, signals, player settings, and other Godot-specific nodes stay in Godot.
- Full conventions, MCP material examples, reimport commands, validation, limitations, and troubleshooting are in `Docs/blender_pipeline.md`. Update that document, and this section if the rule changes, when a new pipeline limitation is confirmed.
- The separate humanoid test base uses `Assets/Characters/BaseHumanoid/Source/Humanoid_Base.blend` as source and generated male/female GLBs under `Exports/`, as explicitly requested for that asset. Regenerate them with `Tools/Blender/HumanoidBase/export_base.py`; do not rebuild manual source edits or edit the GLBs. Validate `Humanoid_Base_Test.tscn`. This exception does not change the Level_01 direct `.blend` pipeline or authorize Player integration.
- The later authorized Main Character V2 POC uses PoseLab as source and `BH01_Male_V2.glb` as generated runtime output. Preserve manual Actions; capture/bake only the selected authored poses through `capture_v2.py` / `export_v2.py`. Keep its one deform skeleton and isolated presentation module; retain the legacy toggle. See `Docs/MAIN_CHARACTER_V2_POC.md` and the V2 section in `Docs/blender_pipeline.md` for validation and the inherited mesh-selection restriction.
- V2 FP camera position follows the animated non-deforming `FP_CAMERA_SOCKET` under `chest`. Capture/export writes shared socket offsets in rig axes plus both PoseLab FOVs; no per-Action absolute camera heights. Read the socket after AnimationPlayer.Advance; preserve mouse-look parents and never inherit socket rotation. Godot `.tscn` Transform3D serialization uses basis rows; validate actual runtime camera/bow transforms after writing calibration.
- V2 locomotion authoring exports explicit `V2_EXTRA_ACTIONS` over their complete Action ranges/FPS, including the animated socket. Idle/Slide retain frame-1 static semantics. Keep `animation/remove_immutable_tracks=false` and the V2 animation metadata import hook; dropping rest-valued tracks leaks the previous clip's pose across transitions. See `Docs/V2_LOCOMOTION_AUTHORING.md` for loop and authoring workflow.
- Current default is V4 split: `MainCharacter1POV.tscn` renders ARMS + FP_CyberBow only; `MainCharacter3POV.tscn` is an independent full-body visual consumer with World_CyberBow. No world body/legs enter normal FP, even in Slide. Layer 17 is full world body/bow, 19 is FP in its own World3D; 18 is legacy-only. Gameplay camera never reads either visual skeleton. One read-only state observer routes two `SplitAnimationSlots` resources; clips cannot own gameplay timing. See `Docs/SPLIT_PRESENTATION_V4.md`.
- PoseLab keeps its legacy scene/Actions and adds independent `BH01_1POV` / `BH01_3POV` scenes, rigs, CAM_1POV/CAM_3POV and `BH01_1POV_*` / `BH01_3POV_*` Actions. Do not overwrite authored indexed Actions with setup_split.py. Use capture_split.py with explicit SPLIT_BRANCH, then export_split.py --branch 1POV/3POV; BH01_1POV.glb and BH01_3POV.glb are generated. Preserve immutable tracks and metadata hook. Preserve matrix_parent_inverse when copying bow parents, or right-hand nock IK moves despite unchanged keys. Fixed CAM_1POV exports framing separately; it must not follow animated bones.
- V2/V3 remain reference paths: F12 switches split / V3, then F11 selects V3/V2 and F9 legacy. V3 uses `LegacyHybrid1POV.tscn` and unchanged `MainCharacterV3.FPDrift.cs`; its old slide-world-legs behavior is fallback only. V4 preserves accepted drift math in `MainCharacterV4.FPDrift.cs`: neutral animation/wrist first, common-root drift after, interpolation OFF. F4 toggles drift, F6 audio panel, F7 mute. Do not repurpose those audio keys. Original V2 assets, Actions and camera/socket export remain untouched by split exports.
